# v4.3 — the logbook (detailed design)

The board is a cockpit for live work. At hundreds of runs, the answer is
separation (active vs archive), not scrolling — and the payload must shrink
before the UI does: today `/api/fleet` ships **every event of every run ever**,
which falls over long before the grid looks crowded.

**Design decision (simplification):** closed = archived, immediately. No N-day
timer. Rationale: with v4.1's hatching, a just-closed card is still visible in
the All view; the Active view excludes closed instantly; a timer adds config and
ambiguity for zero benefit. (Supersedes the roadmap's "auto-archive after N days".)

---

## A. Fleet payload diet

`GET /api/fleet?view=active|all` — default `active`.

- `view=active`: tasks where `status != 'closed'`, their runs, and events for
  those runs only, **capped at the last 40 events per run** (card shows 8; the
  modal refetches full — see C). machines/repos/captures/groups/daemon/providers
  unchanged.
- `view=all`: previous behavior (everything, uncapped). Kept as an escape hatch
  and for the e2e; document in the release notes that it can be slow on old DBs.
- Response adds `counts: { activeTasks, closedTasks }` (for the header seg badge).

Event capping must happen per run in SQL or in the grouping loop — do NOT load
all events then slice (that's the bug being fixed). Drizzle: query events with
`inArray(agentEvents.runId, activeRunIds)`; per-run cap in the loop is acceptable
if the query is already scoped to active runs (the dominant win is scoping).

**WS is unchanged** (live broadcasts only concern live runs). Board-side guard:
an incoming `event`/`run` message for a runId not in the `runs` map and not
`status:'pending'` is ignored (archived runs never resurrect via WS).

## B. Board: Active / Archive views

Header, next to the ws pill: a two-option seg (reuse `.seg`, compact):

```html
<div class="seg view-seg" id="viewSeg">
  <button class="seg-opt on" data-view="active">Active</button>
  <button class="seg-opt" data-view="archive">Archive <span id="archN" class="seg-hint"></span></button>
</div>
```

- Active: today's board (grid + v4.2 bands), hydrated from `?view=active`.
- Archive: the grid region swaps to a list (`#archList`), lazily fetched.

## C. Archive list

**API**: `GET /api/archive?offset=0&limit=50&q=&repo=&status=`
Rows = closed tasks, newest first:

```json
{ "total": 132, "rows": [{
  "taskId": 41, "title": "…", "repoName": "coxpit-oss", "groupTitle": "…|null",
  "closedAt": 0, "runs": [{"id": 97, "status": "merged", "filesChanged": 3, "agent": "codex", "model": ""}]
}]}
```

Filters: `q` = LIKE on title; `repo` = repo id; `status` = a run status the task
must contain (e.g. `merged`). All optional. `limit` clamped ≤ 100.

**UI**:

```html
<div class="arch-bar"><input id="archQ" placeholder="search title…"/><select id="archRepo">…</select></div>
<div class="arch-row" data-t="41">
  <span class="ar-title">fix auth flow</span>
  <span class="ar-runs">r97 merged · r98 done</span>
  <span class="ar-repo">coxpit-oss</span>
  <span class="ar-date">08-18</span>
</div>
<button class="btn-ghost sm" id="archMore">load 50 more</button>
```

CSS: single-line rows, mono data fields, hover highlight; mobile stacks
title/runs on one line, repo/date fade (`.ar-repo{display:none}` ≤ 860px).
Search debounced 300ms; filters reset offset.

**Row click** → task drawer: reuse the run modal. Fetch `GET /api/tasks/:id`
(already returns task + runs + events per run — verify; if events missing, add
them there), insert those runs into the client `runs`/`tasks` maps, then
`openModal(firstRunId)`; the modal's existing Compare/diff/docs work unchanged
(diff will say worktree gone; Rendered falls back to v4.1 snapshots — this is
where the library pays off).

## D. Run modal full-timeline fetch

Because fleet now caps events at 40, `openModal` must fetch the complete record:
on open, `GET /api/runs/:id` and replace that run's `events` in the client map
before `paintModal()`. (Also fixes an existing subtle gap: very chatty runs
already exceed what the card buffer shows.)

## Compatibility

- The desktop app always loads the board from its own daemon — no skew.
- Any external consumer of bare `/api/fleet` sees `active` by default after
  upgrade; release notes must call this out loudly with the `?view=all` remedy.
- e2e keeps most checks on `view=all` semantics? **No** — e2e should exercise the
  default path. Update assertions that relied on closed tasks appearing in fleet
  (the task-close check) to query `?view=all` explicitly.

## e2e additions

1. Close a task → default fleet omits it; `?view=all` includes it; `counts.closedTasks ≥ 1`.
2. `GET /api/archive` returns the closed task row; `q=` filter matches/misses.
3. Event cap: insert >40 events is impractical dry — instead assert the fleet
   response for an active run has `events.length ≤ 40` (trivially true) AND
   `GET /api/runs/:id` returns ≥ the fleet count (full record path exists).
4. Board HTML contains `id="viewSeg"` and `arch-row` styles.
