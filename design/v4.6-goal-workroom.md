# v4.6 — the Goal workroom (detailed design)

A Goal (a plan-fan-out group, `task_groups.kind='goal'`, or a swarm group) is today a
passive board band with batch actions. This milestone gives a Goal a **single room you
open from the band** — one place that aggregates every sibling run and lets you drive the
whole goal: spawn more attempts, broadcast a follow-up to the settled runs, converge them,
or just ask a read-only coordinator what's going on.

**Owner-first, built on what exists.** No new orchestration subsystem. The room composes
three primitives already in the tree: **groups** (`task_groups` + `tasks.groupId`),
**run sessions** (`steerRun`, resume via `agentRuns.sessionId`), and **self-orchestration /
fan-out** (`planFanout`'s task-launch loop). New surface area is small: 4 thin endpoints,
one nullable column (L2 only), and one modal.

**Visual source of truth:** the approved mockup — `scratchpad/goal-workroom-mock.html`
(hosted: the Goal-workroom artifact). Match its layout and the board's existing tokens
(`--brand #4ec9b0`, `--s-*` status colors, `.chip`, `.seg/.seg-opt`, `.btn/.btn-ghost`,
`.gband*`). Dark + mono, semantic status color separate from the accent.

**Ship as two layers inside one milestone:**
- **L1 — deterministic core** (no new agent): aggregate view + `+ New attempt` (spawn into
  group) + `→ Broadcast` (steer settled runs) + surface existing review/integrate. This is
  most of the value and is pure plumbing over existing functions.
- **L2 — Ask coordinator**: a read-only, resumable Q&A agent scoped to the group. Adds the
  "conversation" feel; never takes actions.

Sequencing: this is **4.6.0**, cut together with the already-committed 4.5.1 changes on
`main` (landing wrap fix, contribution docs, CI hardening, Browse greenfield). No standalone
4.5.1 tag — npm goes 4.5.0 → 4.6.0 (batch rule; CI runs only on `v*` tags).

## ⚠️ Correction to the mockup (important)

`steerRun` (orchestrator.ts) only steers a **settled** run (`done`/`failed`/`stopped`) that
has a `sessionId` and a live `worktreePath`. A **running** run is rejected
(`still running — attach the terminal to intervene`), and **dry-run** runs have no session.

So **Broadcast targets the group's settled, steerable runs** — not live ones. The mockup's
"라이브 2건에 steer" and the "정착 run도 포함" checkbox are wrong. Implement it as:

- Broadcast steers every group run that is `done`/`failed`/`stopped` **and** has `sessionId`
  **and** still has a worktree. Running runs are **skipped** and reported
  (`3 steered · 2 still running (steer after they settle) · 1 dry (no session)`).
- Drop the "정착 run도 포함" checkbox. Instead the composer shows a live count
  (`N steerable now · M still running`) so the honest scope is visible.
- While runs are live, the primary Work verb is **`+ New attempt`** (always available);
  Broadcast and Converge come into their own once runs settle. This matches "both live and
  post-settle" — spawn during, steer/converge after.

(A future nicety — queue a broadcast to apply to running runs on settle — is explicitly out
of scope for 4.6; note it in a code comment only.)

## A. Data model

Reuse `task_groups` (`id`, `kind 'goal'|'swarm'`, `title`) and `tasks.groupId` as-is.

**L2 only** — add one nullable column for the coordinator's resumable session, following the
idempotent-DDL pattern in `src/db/index.ts`:

```sql
ALTER TABLE task_groups ADD COLUMN coord_session_id TEXT NOT NULL DEFAULT '';
```

Mirror in `src/db/schema.ts` (`coordSessionId: text('coord_session_id').notNull().default('')`).
L1 touches no schema.

## B. Server API (`src/server.ts`, orchestrator helpers in `src/orchestrator.ts`)

All under the existing auth gate. Group id is `:id` (a `task_groups.id`).

### B1. `GET /api/groups/:id` — aggregate view (L1)

Powers the room's chips + timeline. Keep it focused (payload-diet philosophy from v4.3).

```
200 {
  group: { id, kind, title, coordSessionId? },
  runs: [ { runId, taskId, title, status, agent, model, branch, filesChanged,
            live: boolean, steerable: boolean } ],   // steerable = settled + sessionId + worktree
  events: [ { runId, kind, payload, ts } ]           // merged across the group's runs,
                                                       // newest-last, cap 200 most-recent
}
404 { error: 'group not found' }
```

- `runs`: join `tasks` (groupId=:id) → their `agentRuns`. `live` = `liveChildren.has(runId)`
  (export a tiny `isRunLive(id)` from orchestrator, or a status check). `steerable` per the
  steerRun preconditions above.
- `events`: `agentEvents` for those runs, ordered by id, capped to the last 200 — the room
  shows recent activity, not full history (open a run for its full timeline).

### B2. `POST /api/groups/:id/spawn` — "+ New attempt" (L1)

```
body { title?: string, prompt: string, count?: number (1..5, default 1), real?: boolean }
201 { ok: true, tasks: [ { id, title, runId } ] }
400 { error } (no prompt) · 404 (group not found)
```

- Reuse `planFanout`'s inner loop. **Refactor**: extract the "create task with groupId +
  create run + broadcast + launchRun" body into an exported helper
  `launchGroupTask(groupId, repoId, title, prompt, real): Promise<{id,title,runId}>`; call it
  from both `planFanout` and here. `repoId` comes from any existing task in the group (all
  siblings share a repo).
- `title` defaults to `prompt.slice(0,40)`. `count>1` launches N attempts of the same
  prompt (attempt counter chips already exist from v4.2).
- Dry inheritance: pass `real` through; default `false` (rehearsal-safe) unless the group's
  runs were real — simplest is to honor the `real` flag from the body (the board sends the
  current dry/real toggle), matching how `/api/plan` and `/api/tasks/:id/run` already work.

### B3. `POST /api/groups/:id/steer` — "→ Broadcast" (L1)

```
body { message: string, mode?: 'work'|'ask' (default 'work') }
200 { ok: true, steered: number, skipped: [ { runId, reason } ], detail: string }
400 (empty message) · 404 (group not found)
```

- Load the group's runs; for each, call the existing `steerRun(runId, message, mode)`.
  Aggregate: `ok` → steered++, else push `{runId, reason: detail}` to `skipped`.
- Runs are steered concurrently (`Promise.all`), but cap fan-out to a small pool if a group
  is huge (not expected; a `for` loop is fine at these sizes).
- `detail` is a human summary: `"3 steered · 2 still running · 1 no session"`.
- This reuses steerRun wholesale — no new orchestration. `mode:'ask'` here means "ask each
  run about its own work" (per-run), which is different from B4's group-level coordinator.

### B4. `POST /api/groups/:id/ask` — read-only coordinator (L2)

```
body { message: string }
200 { ok: true, answer: string }
400 (empty) · 404 (group not found)
```

- Read-only. **Never** writes files, opens a worktree, or launches a run. Model it on
  `reviewTask` (which already reads settled run diffs) but conversational + resumable.
- Build context: for each group run, gather `{title, status, agent, filesChanged}` and, for
  settled runs, a **bounded** diff/summary (reuse `getRunDiff`, cap each to ~1500 chars,
  cap total to ~12k). Prepend a system-ish preamble: "You are a read-only coordinator for a
  goal with these parallel attempts. Answer the question. Do not propose running commands."
- Resume: store/reuse `task_groups.coord_session_id`. First call: run the agent one-shot
  (`config.agent.bin -p <prompt> --output-format json`), capture its `session_id`, persist.
  Later calls: `provider.resumeCmd(coordSessionId, message)` so it's a real conversation.
  Add an orchestrator export `askGroupCoordinator(groupId, message, real)`.
- Dry mode (`real=false` / `COXPIT_AGENT_REAL` off): return a deterministic mock answer
  (like planFanout's dry branch) and a synthetic session id, so e2e stays credit-free.
- Token guard: the diff cap above; if the group is large, summarize counts instead of diffs.

### B5. Converge — reuse, don't rebuild (L1)

No new endpoint. The room's "Converge" surfaces the **existing**:
- `POST /api/tasks/:id/review` (AI review judge) — or loop it across the group's tasks.
- `integrateRuns(runIds)` via the existing integrate path (v4.2 group action) with the runs
  the user selects in the room.
- Existing per-run merge/export from the run view (chip → open run).

If a single "review the whole group" call is wanted, add a thin
`POST /api/groups/:id/review` that loops `reviewTask` over the group's tasks and concatenates
— but prefer reusing the per-task review the board already renders. Keep L1 minimal.

## C. Board — the Goal workroom (`src/board.ts`)

> `board.ts` is one big template literal. Client newlines are `\n` in source; never leave an
> unescaped backtick or `${`. Use `esc()` for text, `escA()` for attributes.

### C1. Entry

In the group band header (`.gband-h`), add a button **`⌒ Open workroom`** (`.btn-ghost sm`)
next to the existing fold/actions. Clicking opens the room for that `groupId`. (Optionally
also make the band title clickable.) Show it for any group (goal or swarm) with ≥1 task.

### C2. Modal `#groupRoomOverlay`

Match the mockup. Reuse existing classes where they exist; add room-specific ones:

- `.overlay` (existing) wrapping `.room` (new): `width:min(920px,96vw); max-height:90vh;
  display:flex; flex-direction:column`, surface bg, `--line` border, radius 16.
- **Header** `.rh`: `⌒` glyph (brand) · title `Goal: <title>` · count `· N runs · X done · Y
  running` · `×` close. Band-tint background (`linear-gradient(180deg,var(--brand-dim),
  transparent)`).
- **Chips** `.chips`: one `.chip` per run — status dot (reuse `.chip i` + status class),
  `rN` label, brief meta (`done · +A−B` or `agent · editing…`). Running → pulse (existing
  `.chip.running i` animation, already `prefers-reduced-motion` guarded). A just-spawned run
  = `.chip.new` (dashed brand border). **Clicking a chip opens that run** in the existing run
  modal (reuse `openModal(runId)` / whatever the run view opener is).
- **Body** `.body`:
  - Work: `.feed` — merged timeline, one `.fl` per event, `who` colored by run
    (`.who.rN` → status color), `goal →`/`goal ＋` markers in brand (`.fl.mark`). Humanize
    events with the existing `humanize()`; render group-level actions (spawn/broadcast) as
    `goal` lines.
  - Ask (L2): `.conv` — you / coordinator turns; read-only note under each coordinator answer.
- **Composer** `.composer`:
  - `.seg` toggle `✎ Work | ? Ask` (reuse `.seg/.seg-opt`, `.on` = active). (If L2 not yet
    shipped, render Work only — hide the toggle.)
  - `.seg-hint` line. In Work, show the honest steer scope: `N steerable now · M still running`.
  - `<textarea>` composer.
  - Work verbs `.verbs`: `＋ New attempt` (`.btn-ghost`), `→ Broadcast` (`.btn-ghost`),
    grow spacer, `Converge ▾` (`.btn`, opens a small menu: *Review group* · *Select runs to
    integrate*). **No "정착 run도 포함" checkbox** (see correction).
  - Ask send-only row: read-only note + `Ask` button.

### C3. Wiring

- Open: `GET /api/groups/:id` → render chips + feed; subscribe to live updates (C-D).
- `＋ New attempt`: prompt for title/prompt (reuse the existing task-compose inputs pattern,
  or a small inline form in the room) → `POST /api/groups/:id/spawn` → new chip appears via WS.
- `→ Broadcast`: textarea → `POST /api/groups/:id/steer` → toast the `detail` summary
  (`3 steered · 2 still running`); steered runs flip to `running` via WS.
- `Converge ▾`: *Review group* → existing review flow; *Integrate* → existing multi-select
  integrate over the group's runs.
- Ask (L2): textarea → `POST /api/groups/:id/ask` → append coordinator turn.
- `Esc` closes the room (add `#groupRoomOverlay` to the existing global Escape handler).

### D. Live updates

The room reuses the existing WS `hub`. On open, build a `runId→inGroup` set from the aggregate
response; the room's WS handler filters broadcasts (`type:'run'|'event'|'task'`) to that set
and (a) updates/adds chips, (b) appends feed lines. A spawned run arrives as a `run` event
with the new `runId`; add its chip (`.chip.new`) and a `goal ＋` feed line. Keep the set fresh
when spawn responses return new run ids.

## E. Edge cases & guardrails

- **Read-only Ask never acts** — no worktree, no launch, no file writes. The preamble +
  `ask`-style wrapping enforce intent; the endpoint simply never calls launch/steer.
- **Group with one task**: room still opens (thin) — fine; entry may be most useful at ≥2.
- **Steer skips**: running / no-session (dry) / worktree-cleaned runs are reported, never
  silently dropped (honest-scope principle).
- **Dry runs**: spawn honors `real`; ask returns a mock in dry mode; broadcast on a dry run
  reports `no session` skip.
- **Repo resolution for spawn**: take `repoId` from any existing group task; if the group
  somehow has no tasks, 409 `group has no tasks to inherit a repo from`.
- **Concurrency**: broadcast/ask over many runs — bounded loops; no unbounded fan-out.
- **Token cost (Ask)**: diff context capped (~12k). Large group → counts/summaries, not raw
  diffs.
- **No new non-goals broken**: still no accounts/telemetry/relay; still one self-contained
  board string; external tools stay external.

## F. e2e additions (`test/e2e.sh`)

Add after the existing group/plan checks (reuse the dry `POST /api/plan` that already creates
a group):

1. **aggregate**: capture the plan group id → `GET /api/groups/:id` returns `group`, `runs`
   (≥2, each with `steerable` boolean), `events` array.
2. **spawn**: `POST /api/groups/:id/spawn {prompt}` (dry) → 201, a new task joins the group
   (its `groupId` matches), the run settles `done`.
3. **broadcast**: after the group's runs settle (dry runs have no session) →
   `POST /api/groups/:id/steer {message}` returns `ok:true` with `skipped` listing the
   dry/no-session runs (proves the honest-skip path). If a real-session run exists in the
   harness, assert `steered≥1`; otherwise assert the skip reasons.
4. **ask (L2, dry)**: `POST /api/groups/:id/ask {message}` → `ok:true` + non-empty `answer`;
   second call persists/reuses `coord_session_id` (assert it's non-empty on the group row or
   a stable session in the response).
5. **UI contract**: board HTML contains `id="groupRoomOverlay"` and the workroom seg toggle;
   the group band contains the `Open workroom` control.

Keep the bash-3.2 rules (capture into vars, `case` not `grep -q` on big pipes, `unset TMUX`).

## H. Layering & Definition of done

**L1 (deterministic core) — DoD**
- `GET /api/groups/:id`, `POST /api/groups/:id/spawn`, `POST /api/groups/:id/steer` shipped;
  `launchGroupTask` extracted and shared with `planFanout`.
- Board: `Open workroom` entry + `#groupRoomOverlay` with chips, merged feed, Work composer
  (spawn / broadcast / converge-surface). Live chip/feed updates over WS. Escape closes.
- Broadcast reports honest skips; no misleading "steer live runs" affordance.
- `npm run typecheck` clean; e2e green with checks 1–3 + UI contract; board JS parses
  (render check: no pageerror, room opens, seg present).

**L2 (Ask coordinator) — DoD**
- `coord_session_id` column (idempotent DDL) + `POST /api/groups/:id/ask` + `askGroupCoordinator`.
- Ask mode in the room (read-only conversation, send-only composer). Dry returns a mock.
- e2e check 4 (ask dry + session persistence). Read-only invariant holds (no launch/steer/write
  from the ask path).

**Milestone DoD**: L1 + L2 both merged to `main` as e2e-green commits; then 4.6.0 is cut
(bundling the queued 4.5.1 commits) via the standard train — bump both package.json +
desktop, `npm i --package-lock-only` (root + desktop), commit, tag `v4.6.0`, CI
(now hardened) builds installers + un-drafts, owner `npm publish --otp`, resident upgrade.
