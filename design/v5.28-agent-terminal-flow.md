# v5.28 — agent terminal flow, Part A: agent state & attention (detailed design)

## Why this milestone

Usage says it plainly: the daily surface is the **terminal** (`/cockpit`) — the last
~20 releases (v5.16→v5.27) were all cockpit work, and in practice coxpit is driven as a
terminal for running AI coding agents (claude/codex), not as the fleet board. So the next
milestone deepens the *one thing that's used*: **run many agents from the terminal, and get
pulled back only when one needs you.**

This spec covers **Part A only** — agent state detection + attention. Parts B (stale-process
guard), C (quick actions + safe context injection), D (input/output ergonomics) follow as
separate specs/commits.

Reference discipline (from Giting's measured curation):
- **ruflo** (72k★ multi-agent harness whose 300+ tools are largely *stubs* — agents "spawn"
  as JSON records with no subprocess): the lesson is **ship only what actually works**. State
  here is read from the real PTY stream; when detection isn't confident, it says `idle`, never
  a fabricated `waiting`. No theater.
- **PokeTokenBar** (ambient menubar awareness): inspiration for the passive **Agents rail** —
  glance, don't babysit. Concept only (that repo is unverified `watch`).

## What ships

Each open terminal shows a coarse **agent state** — `working · waiting · idle · exited` —
read from its output stream. Background tabs that turn **waiting** (the agent needs you) or
**exited/done** raise attention: a tab dot + a count on the cockpit, an optional sound, and an
opt-in browser notification. A thin **Agents** rail lists every live terminal with its state
and last activity, so five agents across tabs are one glance, not five check-ins.

Scope honesty: state is tracked **while a terminal is attached** (its `/ws/term` socket is
open — the cockpit keeps one per open tab, focused or not, so backgrounded tabs are covered).
If the whole cockpit is closed there is no stream to read; the optional webhook (A5) is the
only signal in that case, and the spec says so rather than pretending otherwise.

## Part A — agent state & attention

### A1. State model

A per-run coarse state, four values (plus `unknown` before first output):

| state | meaning | how it's decided |
|---|---|---|
| `working` | output is actively streaming | bytes arrived within the last `ACTIVE_MS` (600ms) |
| `waiting` | output stopped **and** the tail matches a high-confidence agent input/permission prompt | quiescent + prompt-pattern hit (A2) |
| `idle` | output stopped, no agent prompt detected (e.g. a shell prompt, or the agent isn't running) | quiescent + no pattern |
| `exited` | the PTY/tmux pane process ended | `term.onExit` (server.ts:1672) |

Every terminal in coxpit is a **run** (free sessions are runs in a `sessions`-bucket repo —
`runIsSession`), so state attaches to the run and rides the existing `/ws` hub like other run
deltas. It is **separate from** the board's `run.status` (`running/done/…`) and from
`latestActivity()` (cockpit.ts:572), which derive from parsed stream-json events — those only
exist for board runs, not for a hand-typed `claude` in a free session. A2 fills exactly that
gap for terminal sessions from raw output.

### A2. Server-side detection (`src/agentstate.ts`, new; tapped in `/ws/term`)

Detect on the **server**, at the output tap already in the `/ws/term` handler
(server.ts, `term.onData(d => socket.send(...))` ~1615). Server-side (not per-client) so the
state is one source of truth regardless of how many clients are attached, survives a client
reconnect, and can feed the webhook.

New module `src/agentstate.ts`:
- `feed(runId, chunk)` — called from `term.onData` with each raw output chunk. Keeps a small
  rolling tail buffer per run (last ~8KB, ANSI left intact — patterns match on the raw TUI),
  stamps `lastByteAt = now`, and sets `working` (debounced: only broadcasts a change, not every
  chunk). Arms a timer at `ACTIVE_MS`; when it fires with no new bytes, runs `classifyIdle()`.
- `classifyIdle(tail)` → `waiting | idle`. **Conservative, pattern-based, best-effort.** A
  small library of high-confidence prompt patterns, e.g.:
  - claude-code: a permission prompt (`Do you want to proceed?`, a numbered `❯ 1. Yes` /
    `1. Yes` / `2. No` block), or the idle input box with no trailing `esc to interrupt`.
  - codex: its approval prompt / input affordance.
  - Presence of `esc to interrupt` (or an active spinner frame) in the tail ⇒ still `working`,
    not idle — the agent is mid-task.
  Anything not matched ⇒ `idle`. **Never guess `waiting`.** Patterns live in one table with a
  comment that they are heuristic and provider-TUI-specific; adding a provider = adding a row.
- `onExit(runId)` — from the handler's `term.onExit`; state `exited`.
- `drop(runId)` — on socket close with no other attachers; stop timers, keep last state briefly
  for the rail then clear.

Guard against fly-wheeling: coalesce state changes (a `working`↔`idle` flap under `FLAP_MS`
≈1.5s is suppressed); only a *stable* transition broadcasts.

### A3. Broadcast & transport (`src/hub.ts`, `src/server.ts`)

- New hub message: `broadcast({ type: 'agentstate', runId, state, detail, ts })` where `detail`
  is a short human string for the rail (`"waiting: approve edit?"`, `"working: Edit src/x"` —
  best-effort from the tail, sanitized/clipped, no secrets).
- `GET /api/fleet` gains a compact `agentStates` map (`runId → {state, detail, ts}`) so a fresh
  cockpit load / reconnect paints current state without waiting for the next delta.
- Only session/terminal runs carry this; board runs keep using their event-derived
  `latestActivity`. The cockpit merges: if a run has an `agentstate`, it wins for the terminal
  surfaces; otherwise fall back to `latestActivity`.

### A4. Cockpit surfaces (`src/cockpit.ts`)

- **Tab dot**: each terminal tab shows a state dot — `working` blue, `waiting` amber (pulses),
  `idle` grey, `exited`/done green. Semantic colors, **distinct from the `--brand` teal accent**
  (accent stays for focus/primary action only). A waiting *background* tab also shows a small
  `◔ 대기` marker; the cockpit header/title carries a count of waiting tabs.
- **Agents rail** (new, thin, left of the tab area or foldable): one row per live terminal —
  state dot + name + `detail`, `waiting` rows tinted amber and sorted to the top. Click a row →
  focus that tab. This is the PokeTokenBar-style ambient glance. It reads from the same
  `agentStates` the tabs use; no extra polling.
- Wire into the existing render path: extend `latestActivity`'s consumers
  (renderTabs, the `[data-role=act]` pane-act slot ~975/1162, the tree `.ract` ~689) and add a
  `paintAgentState(runId)` fed by the `agentstate` ws message inside `wsConnect().onmessage`
  (cockpit.ts ~1777, which currently just `scheduleHydrate()`).
- **Focus-mode aware**: the rail hides with the tree in focus mode (`.layout.focusmode`), but
  the tab dots and the waiting count stay — attention must survive focus mode.

### A5. Attention delivery (opt-in, reuse existing plumbing)

A transition **to `waiting` or `exited` on a non-focused tab** raises attention. All opt-in,
off by default, remembered in `localStorage`:
- **Tab + rail** (always on): the visual state above.
- **Sound** (`coxpit.sound`): a short cue on the raising transition; never for the focused tab.
- **Browser notification** (`coxpit.notify`): reuse the board's exact pattern
  (board.ts:2246 — `Notification.requestPermission`, `localStorage 'coxpit.notify'`, the bell
  toggle). Fire when the document is hidden or the tab is unfocused; body =
  `"<session> · 입력 대기"` / `"<session> · 완료"`, clicking focuses that tab.
- **Webhook / push** (server, reuse `config.webhookUrl` + `COXPIT_PUBLIC_URL`): the only signal
  when the cockpit is fully closed. On a `waiting`/`exited` transition, POST the same settle-
  webhook shape used for board runs, with `{event:'agentstate', runId, state, url}`. Off unless
  `webhookUrl` is set (already the case). Documented limit: needs a client attached to have
  produced the stream in the first place; a truly closed cockpit with no attachers sees nothing.

Settings: a small "Agents" section in cockpit settings — sound on/off, notify on/off (drives
the permission prompt), and which transitions ping (waiting / done / both).

### A6. Honesty guardrails (the ruflo lesson, encoded)

- State is derived from **real output**; there is no code path that sets `waiting`/`done`
  without a stream event or `onExit` behind it.
- `waiting` requires a **positive pattern hit**; absence of a pattern is `idle`, never `waiting`.
- The pattern table is small, commented as heuristic, and provider-TUI-specific — no claim of
  understanding the agent's intent, only "the screen shows an input/permission prompt."
- No persistence of fabricated history, no "self-learning": the tail buffer is in-memory and
  ephemeral.

## Phasing (each an e2e-green commit; dry-safe; no build step)

1. **Detection core** — `src/agentstate.ts` (`feed`/`classifyIdle`/`onExit`/`drop`, timers,
   flap-suppression) + the `term.onData`/`onExit` taps in `/ws/term`. Unit-style e2e: pipe a
   canned claude-permission tail through `feed`, assert `waiting`; pipe shell-prompt tail, assert
   `idle`; assert `esc to interrupt` tail stays `working`.
2. **Transport** — `agentstate` hub message + `agentStates` in `/api/fleet`; e2e asserts the map
   shape and that a session run carries it while a board run does not.
3. **Cockpit surfaces** — tab dots, waiting count, `paintAgentState`, the Agents rail (+ focus-
   mode rule). e2e: `/cockpit` contains the rail markup + dot classes + the `agentstate` handler.
4. **Attention** — sound + notification (reuse board pattern) + settings section; webhook branch
   on the server. e2e: settings markup present; webhook fires on a simulated transition when
   `webhookUrl` is set.

## Guardrails

- Terminal-only, no board dependency; no new native deps; no build step (single-file cockpit
  string stays framework-free).
- Semantic status colors are **separate from `--brand`**; attention reads on the dark ground.
- Everything opt-in and quiet by default; the focused tab never pings itself.
- Detection is best-effort and said to be; a wrong `idle` is acceptable, a fabricated `waiting`
  is not.
- No secrets in `detail` or the webhook (sanitize/clip the tail).

## Definition of done

- Open `claude` in two free-session tabs; work in one. The other tab's dot goes `working` →
  `waiting` when its agent asks a question, the cockpit shows `1 대기`, and (opt-in) a
  notification/sound fires because that tab isn't focused.
- The Agents rail lists both with live state + detail; clicking a row focuses the tab.
- A finished agent turns the tab green and (opt-in) pings once.
- No state is ever shown that wasn't behind a real stream event; `waiting` only on a pattern hit.
- Full e2e green; `/cockpit` client JS passes `node --check`; typecheck clean.

## Later parts (separate specs)

- **B — stale-process guard** (DeskBox's stale-build rule): "what's actually running on this
  port/path" so a restarted agent build isn't debugged against the old process.
- **C — quick actions + safe context injection** (ai-job-search injection discipline): one-tap
  start/resume + quick replies; injected file/selection treated as data, not instructions.
- **D — input/output ergonomics**: multi-line paste, mobile input bar, clickable paths/diffs →
  viewer.
