# v5.1 — close the loop (landing as a phase)

**Theme:** the run lifecycle stops at `done`, but the real end is *landed on origin*.
Today the last mile — conflict resolution and integration — lives **outside** coxpit, so
the thread breaks: you do the work in the app, watch it on a run card, then drop to a bare
terminal and fire up a **context-less** agent to reconcile against origin. The run card is
loved for visibility, but it only covers *launch → settle*, not *launch → landed*.

This milestone extends the lifecycle through **integrating → landed**, keeps the last mile
in-app (resume the run's *own* agent, which still has the context), and lands on the real
target (origin branch + PR).

**Field report that drove this** — owner ran r10–r13 (EduWorks tutor-announcement features)
through coxpit on the desktop app. Small diffs, but the local `main` the worktrees branched
from had drifted ~398 commits from `origin/develop`; `mergeRun`'s whole-branch
`git merge --no-ff` exploded into 14-file conflicts in files the runs never touched. The
owner escaped to a manual terminal + a fresh `claude` to cherry-pick the runs' unique commits
by hand. Brief: `docs/` (owner upload, 2026-08-20). Line refs verified against v5.0.3 source.

**Decisions (owner, 2026-08-20):**
- **Land target = push branch to origin + open a PR** (matches the workspace rule: no direct
  `main` merge, everything via `develop`→`main` PR). Reuse the v2.6 PR-mode primitive.
- **Default conflict resolver = resume the run's own agent** (`sessionId`) with a targeted
  prompt; the hands-on workbench is the fallback.

**Lifecycle:** `working → settled(done/failed/stopped) → integrating → landed`.
New status vocabulary: `blocked` (settled at exit 0 but did nothing it was asked to),
`integrating`, `landed`. Added as idempotent schema notes; the board renders each distinctly.

The four gaps from the brief are the primitives of this loop:
③ preview = the front gate · ② blocked/no-op = the missing "needs a hand" signal ·
① origin-aware land + cherry-pick = the destination · ④ sibling overlap = land ordering.

---

## Part A — visibility gates (cheap, ship first) · brief ③ ② ④

You cannot close a loop you cannot see. Three read-only signals, no new merge behavior.

### A1. Conflict preview before you commit to a merge (③)
- `git merge-tree --write-tree --name-only <base> <branch>` (git ≥ 2.38) computes the merged
  tree **without a working tree and without a commit**; a non-zero exit + the file list ⇒
  conflicts. Feature-detect; on older git, show "preview unavailable" (don't block).
- New `GET /api/runs/:id/merge/preview` → `{ clean:boolean, conflicts:string[] }`, plus a
  group-level roll-up. The board shows the conflicted-file set **before** the Merge button
  does anything — the 398-commit explosion becomes visible up front, not after an abort.

### A2. `blocked` / no-op runs stop hiding as `done` (②)
- `orchestrator.ts:424` sets `status = code===0 ? 'done'` — an agent that ends its turn asking
  for merge approval exits 0 and is filed `done` with `filesChanged=0`. `taskCloseRisk():1291`
  only flags `filesChanged>0`, so these close **silently**.
- At settle: if `code===0 && filesChanged===0`, look for an approval-required / permission-denied
  marker in the run's stream → mark `blocked`; otherwise render a distinct "no changes" chip on
  the card. `taskCloseRisk` must also surface a `done`/`blocked` run whose task intended a
  write/merge but changed nothing.

### A3. Sibling overlap + land order (④)
- Within a group, per run `git diff --name-only <base>..<branch>`, intersect across siblings ⇒
  the overlapping-file set and a **suggested land order** (fewest-overlap first). Shown on the
  group band before integration — so you plan the sequence instead of discovering it in conflicts.
  (Today only a *planner prompt* at `orchestrator.ts:927` hints "minimize overlap"; there is no
  signal at integration time.)

## Part B — the integration workroom (the loop) · brief ① (resume half)

Merge stops being a one-shot button and becomes a **phase**:

```
Merge ─► preview (A1) ─► clean?  ── yes ─► land (Part C)
                          │
                          no ─► INTEGRATION WORKROOM (same worktree)
                                  ├─ resume the run's own agent (sessionId):
                                  │    "fetch origin, merge origin/<base>,
                                  │     resolve conflicts in <files>, commit."
                                  │    status → integrating · card tracks it · attach terminal
                                  ├─ re-run preview when it settles ─► loop until clean
                                  └─ fallback: "Open as workbench" (in-app terminal + claude)
```

- **Never send the user to a bare external terminal.** The whole point: the agent that just
  did the work still has the context — resume *it*, in *its* worktree, on the card. The
  hands-on workbench (owner's secondary pick) is one click away for the cases a human wants it.
- Reuses `steer`/resume (`sessionId`), the existing terminal attach, and `openWorkbench`.

---

## Part C — origin-aware landing · brief ① (destination half)

- **Drift detection at worktree creation** (`orchestrator.ts:335/864`): if the base has an
  upstream, compute `git rev-list --left-right --count <base>...<upstream>` and surface
  ahead/behind on the card; warn when the base is behind origin — the trap that made the merge
  explode is shown the moment the run is born.
- **Land = to origin, via PR:** fetch origin → rebase the branch onto `origin/<base>` (or
  cherry-pick `<base>..<branch>` unique commits onto a fresh origin-tracking branch — the
  owner-verified safe path) → resolve via Part B if needed → push the branch → open a PR with
  `gh` (reuse v2.6 PR mode). Card end state = `landed` with the PR link.
- coxpit never treats local `main` as the ship target; `origin` is the destination.

---

## Definition of done
A run card spans **launch → landed**: you can preview conflicts, and when they happen you
resolve them by resuming the run's own agent (or a one-click in-app workbench) without ever
leaving coxpit, then land on origin as a pushed branch + PR. `blocked`/no-op runs are visible,
not silent. Sibling overlap is shown before integration.

## Guardrails
- **Dry-run stays sacred**: preview + land must degrade explicitly in dry-run (no origin push
  on a dry parent); e2e is dry-green.
- Merge safety unchanged: clean-base guard, conflict auto-abort remain the floor; the loop adds
  a resolve path, it doesn't remove the guard.
- No new deps; `gh` and `git` stay external (spawned, never vendored). PR mode requires `gh` on
  PATH — feature-detect and guide when absent.
- Schema changes are idempotent ALTERs; never drop/rename columns. New statuses are additive.
- DESIGN.md is the UI contract — the preview panel, the `blocked` chip, the integration
  workroom, the land/PR affordance each land in its table in the same commit.

## Sequencing
**A (gates) → B (workroom) → C (origin land).** A is cheap and immediately relieves the pain
(you *see* the explosion and the no-op before they bite); B keeps you in-app to resolve; C
lands on the real target. Ship as e2e-green commits on main, cut **5.1** once the loop closes.
Design-as-Fable / build-as-Opus continues.
