# v5.1 — close the loop (landing as a phase)

**Theme:** the run lifecycle stops at `done`, but the real end is *landed on origin*.
Today the last mile — conflict resolution and integration — lives **outside** coxpit, so
the thread breaks: you do the work in the app, watch it on a run card, then drop to a bare
terminal and fire up a **context-less** agent to reconcile against origin. The run card is
loved for visibility, but it only covers *launch → settle*, not *launch → landed*.

This milestone extends the lifecycle through **integrating → landed**, keeps the last mile
in-app (resume the run's *own* agent, which still has the context), and lands on the real
target (origin branch + PR).

**Field report that drove this** — owner ran r10–r13 (EduWorks tutor-announcement features)
through coxpit on the desktop app. Small diffs, but the local `main` the worktrees branched
from had drifted ~398 commits from `origin/develop`; `mergeRun`'s whole-branch
`git merge --no-ff` exploded into 14-file conflicts in files the runs never touched. The
owner escaped to a manual terminal + a fresh `claude` to cherry-pick the runs' unique commits
by hand. Brief: `docs/` (owner upload, 2026-08-20). Line refs verified against v5.0.3 source.

**Decisions (owner, 2026-08-20):**
- **Land target = push branch to origin + open a PR** (matches the workspace rule: no direct
  `main` merge, everything via `develop`→`main` PR). Reuse the v2.6 PR-mode primitive.
- **Default conflict resolver = resume the run's own agent** (`sessionId`) with a targeted
  prompt; the hands-on workbench is the fallback.

**Lifecycle:** `working → settled(done/failed/stopped) → integrating → landed`.
New status vocabulary: `blocked` (settled at exit 0 but did nothing it was asked to),
`integrating`, `landed`. Added as idempotent schema notes; the board renders each distinctly.

The four gaps from the brief are the primitives of this loop:
③ preview = the front gate · ② blocked/no-op = the missing "needs a hand" signal ·
① origin-aware land + cherry-pick = the destination · ④ sibling overlap = land ordering.

## Part A — visibility gates (cheap, ship first) · brief ③ ② ④

You cannot close a loop you cannot see. Three read-only signals, no new merge behavior.

### A1. Conflict preview before you commit to a merge (③)
- `git merge-tree --write-tree --name-only <target> <branch>` (git ≥ 2.38) computes the merged
  tree **without a working tree and without a commit**; a non-zero exit + the file list ⇒
  conflicts. Feature-detect; on older git, show "preview unavailable" (don't block).
- **Preview against the land *target*, not the local base** (review C3). A run branched from
  local `<base>` never conflicts with `<base>` — the branch descends from it. The real conflict
  surface is `origin/<target>` (the field report: base `main`, target `origin/develop`). So the
  preview must run against the resolved target **after a fetch** — which means A1 depends on the
  target-resolution + fetch primitive from Part C. Build that primitive first; A1 rides on it.
- New `GET /api/runs/:id/merge/preview?target=origin/<x>` → `{ clean:boolean, conflicts:string[],
  target:string }`, plus a group-level roll-up. The board shows the conflicted-file set **before**
  the Merge/Land button does anything — the 398-commit explosion becomes visible up front.

### A2. `blocked` / no-op runs stop hiding as `done` (②)
- `orchestrator.ts:424` sets `status = code===0 ? 'done'` — an agent that ends its turn asking
  for merge approval exits 0 and is filed `done` with `filesChanged=0`. `taskCloseRisk():1291`
  only flags `filesChanged>0`, so these close **silently**.
- **The deterministic signal is primary** (review C4): `done && filesChanged===0`. The "asking
  for approval" text lives in `lastResult`/`exitSummary` as **natural language**, not a
  structured event (no provider emits a `blocked` event), so phrase-matching is **best-effort
  only** — use it to upgrade the label to `blocked`, but never depend on it. Don't over-promise
  `blocked` precision.
- **Gate the alarm on task intent** (review C5): a `done` run with 0 files is *normal* for an
  `answer`/review task. Use the deliverable contract already in hand (`declaredSet`,
  `orchestrator.ts:657`) — only flag when the declared outputs imply file changes
  (`code`/`file`/`doc`/`page`) or the task was an integration/merge task. Answer-only stays quiet.
- Board renders the flagged run with a distinct "no changes" chip; `taskCloseRisk` surfaces it.

### A3. Sibling overlap + land order (④)
- Within a group, per run `git diff --name-only <base>..<branch>`, intersect across siblings ⇒
  the overlapping-file set and a **suggested land order** (fewest-overlap first). Shown on the
  group band before integration — so you plan the sequence instead of discovering it in conflicts.
  (Today only a *planner prompt* at `orchestrator.ts:927` hints "minimize overlap"; there is no
  signal at integration time.)

## Part B — the integration workroom (the loop) · brief ① (resume half)

Merge stops being a one-shot button and becomes a **phase**. **Critical division of labor**
(review C1): the agent's default sandbox blocks network/git (`orchestrator.ts:119` — the very
reason spawn is file-based, and the reason the original `git merge` stalled on approval). So
resuming the agent to "fetch + merge + push" would hit **the same wall**. Instead:

- **coxpit owns all git** — fetch, rebase/merge attempt, staging, commit, push, PR — via its own
  `runShellOn` (unsandboxed). This is what coxpit already does in `mergeRun`.
- **the agent owns only conflict-marker resolution** — pure file edits inside the worktree,
  which `acceptEdits`/`workspace-write` **do** allow. No git verbs in its prompt.

```
Land ─► fetch + preview vs origin/<target> (A1) ─► clean? ── yes ─► push + PR (Part C)
                                                     │
                                                     no ─► coxpit runs the rebase/merge → leaves
                                                            conflict markers in the worktree
                                                             │
                                                             ▼
                                              INTEGRATION WORKROOM (same worktree)
                                               ├─ resume the run's own agent (sessionId):
                                               │    "resolve the conflict markers in <files>.
                                               │     Do NOT run git — just edit the files."
                                               │    status → integrating · card tracks · attach term
                                               ├─ coxpit stages + continues the rebase/merge
                                               ├─ re-preview ─► loop until clean ─► push + PR
                                               └─ fallback: "Open as workbench" (in-app terminal)
```

- **Never send the user to a bare external terminal.** The agent that just did the work still
  has the context — resume *it*, in *its* worktree, on the card, but scoped to editing files.
  The hands-on workbench (owner's secondary pick) is one click away.
- Reuses `steer`/resume (`resumeCmd`, `providers.ts:60/134`), terminal attach, `openWorkbench`.

## Part C — origin-aware landing · brief ① (destination half)

- **The land target is chosen, not assumed to be the base** (review C2). The worktree branches
  from `defaultBranch` (`orchestrator.ts:335/864`), but the real destination can differ — the
  field report branched from local `main` yet shipped to `origin/develop`. So Land resolves a
  **target branch**: default = the base's upstream (`git rev-parse --abbrev-ref <base>@{u}`) if
  any, else prompt; the user can override. Drift, preview (A1), and rebase all key off this
  **target**, never the base.
- **Drift detection at worktree creation**: if the target/base has an upstream, compute
  `git rev-list --left-right --count <base>...<target>` and surface ahead/behind on the card;
  warn when behind — the trap that made the merge explode is shown the moment the run is born.
- **Land = to origin, via PR:** `git fetch origin` → replay **only the run's own work** onto
  `origin/<target>`. Care (review C6): `mergeRun:776` already merged the base into the worktree,
  so `<base>..<branch>` contains a **merge commit** — a naïve cherry-pick is messy. Prefer either
  `git rebase --onto origin/<target> <base> <branch>` on a branch with no base-merge, **or** a
  clean squash of the net diff (`git diff <base>...<branch>` applied onto a fresh
  `origin/<target>` branch) — one commit, no history drag. → resolve conflicts via Part B if any
  → push the branch → open a PR with `gh` (reuse v2.6 PR mode). Card end state = `landed` + PR link.
- coxpit never treats local `main` as the ship target; `origin/<target>` is the destination.
- **`gh` is required for PR mode** — feature-detect and guide when absent; `git push` alone
  (no PR) is the degraded path.

## Definition of done
A run card spans **launch → landed**: you can preview conflicts, and when they happen you
resolve them by resuming the run's own agent (or a one-click in-app workbench) without ever
leaving coxpit, then land on origin as a pushed branch + PR. `blocked`/no-op runs are visible,
not silent. Sibling overlap is shown before integration.

## Guardrails
- **Dry-run stays sacred**: preview + land must degrade explicitly in dry-run (no origin push
  on a dry parent); e2e is dry-green.
- Merge safety unchanged: clean-base guard, conflict auto-abort remain the floor; the loop adds
  a resolve path, it doesn't remove the guard.
- No new deps; `gh` and `git` stay external (spawned, never vendored). PR mode requires `gh` on
  PATH — feature-detect and guide when absent.
- Schema changes are idempotent ALTERs; never drop/rename columns. New statuses are additive.
- DESIGN.md is the UI contract — the preview panel, the `blocked` chip, the integration
  workroom, the land/PR affordance each land in its table in the same commit.

## Sequencing (revised after review — C1/C3 reorder the naïve "A first")

The truly-cheap, origin-free wins ship first; the origin/target primitive is foundational
because both the preview (A1) and the land (C) ride on it; the agent-resolution loop (B) sits on
top of coxpit-owned git.

1. **Cheap local signals (no origin):** A2 no-op/`blocked` visibility · A3 sibling overlap.
   Self-contained, dry-run-safe, immediate relief for the "silent done" pain.
2. **Foundation:** target resolution (`<base>@{u}`, overridable) + `git fetch` + drift
   (`rev-list --left-right --count`), surfaced on the card.
3. **On the foundation:** conflict preview (A1) against `origin/<target>` + drift warning.
4. **Land (C):** `rebase --onto` / squash onto `origin/<target>` → push → PR (`gh`).
5. **Loop (B):** coxpit drives the merge/rebase; on conflict the agent resolves **markers only**;
   coxpit stages + continues; re-preview → push + PR. Workbench fallback.

Ship as e2e-green commits on main (dry-run-safe throughout; PR/push no-op in dry), cut **5.1**
once the loop closes. Design-as-Fable / build-as-Opus continues.
