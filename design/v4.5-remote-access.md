# v4.5 — remote access (detailed design)

Make reaching the daemon from elsewhere easy, **without coxpit hosting a relay** —
always the user's own Tailscale (primary) or a copy-paste recipe (fallback).
Guardrail, non-negotiable: coxpit detects and *drives* the tool; it never becomes
the tunnel. Keeps "self-hosted, no cloud middleman" intact.

Pinned CLI (Tailscale 1.96.2, macOS, verified 2026-08-19):
- Binary path (mac app): `/Applications/Tailscale.app/Contents/MacOS/Tailscale`.
  On Linux it's just `tailscale` on PATH. Detect both.
- `tailscale status --json` → `.Self.DNSName` (e.g. `coxpit.tailfe5cd2.ts.net.`,
  trailing dot), `.Self.TailscaleIPs[0]`, `.MagicDNSSuffix`.
- Serve (tailnet-only, safe): `tailscale serve --bg <port>` → HTTPS at the DNSName,
  no port. `tailscale serve status [--json]`, `tailscale serve reset`.
- Funnel (public): `tailscale funnel --bg <port>`; `funnel status`, `funnel reset`.
  Public, no Tailscale-side auth → coxpit's own basic auth is the only gate.

Scope: **detection + one-click serve/funnel toggle + copy URL + recipes.** No new
persistent state in the daemon DB — serve/funnel status is read live from the CLI.

---

## A. Detection (server)

New helper `src/remote.ts`:

```ts
export interface RemoteState {
  tailscale: 'missing' | 'stopped' | 'running';
  dnsName?: string;          // trailing dot stripped
  tailnetSuffix?: string;
  serve: boolean;            // serve active for our port?
  funnel: boolean;           // funnel active for our port?
  binPath?: string;          // resolved tailscale bin
}
export async function remoteState(port: number): Promise<RemoteState>
```

Impl:
1. Resolve bin: `command -v tailscale` → else the mac app path (test `-x`).
   None → `{ tailscale: 'missing' }`.
2. `<bin> status --json`:
   - non-zero / "stopped" / "Logged out" → `{ tailscale: 'stopped', binPath }`.
   - parse `Self.DNSName` (strip trailing `.`), `MagicDNSSuffix`.
3. `<bin> serve status --json` and `<bin> funnel status --json` → set `serve`/`funnel`
   true if a mapping points at `http://127.0.0.1:<port>` or `localhost:<port>`.
   (Parse defensively — status JSON shape varies by version; fall back to a plain
   `status` text grep for `:<port>` if JSON parse fails.)

All calls run **on the local machine only** (`runShellOn` with a local target) and
are best-effort with a short timeout; any failure downgrades to `missing`/`stopped`.

## B. API

- `GET /api/remote` → `RemoteState` for `config.port`.
- `POST /api/remote/serve` `{ on: boolean }` → `<bin> serve --bg <port>` / `serve reset`.
- `POST /api/remote/funnel` `{ on: boolean }`:
  - **Guard**: refuse with `409 { error: 'set a password first', code: 'NO_AUTH' }`
    when `config.auth.disabled || config.auth.pass === ''` (Funnel is public; a
    passwordless daemon on the internet = open shells). Serve has no such guard
    (tailnet-only).
  - on → `<bin> funnel --bg <port>`, off → `<bin> funnel reset`.
- All three return the fresh `remoteState(port)` so the board repaints from truth.

Auth: these are behind the normal authGate (owner-only actions).

## C. Board — onboarding "Remote access" card

Placement: the first-run onboarding panel already lists machine readiness
(git·tmux·agent·codex). Add a **Remote access** section below it, and also expose
it when the board is non-empty via a small header affordance (a `🔗` ghost button
next to `#bell` that opens the same card in a `.cfm` dialog `#remoteOverlay`).

States (from `GET /api/remote`):
- `missing` → text: "Install Tailscale to reach this daemon by name from your other
  devices — or use a reverse-proxy recipe below." + link to tailscale.com/download,
  + expandable **Recipes** (see D).
- `stopped` → "Tailscale is installed but not running. Start it, then refresh."
- `running` →
  - Show the base name: `<dnsName>`.
  - **Serve** row: toggle. Off→On calls `/api/remote/serve {on:true}`; when on,
    show `https://<dnsName>` with a **Copy** button + "your tailnet only · HTTPS".
  - **Funnel** row: toggle, styled as the risky option (like the Real-agent seg
    hint). Label "Public internet". If `config.auth` is open, the toggle is
    disabled with a note "set COXPIT_AUTH_PASS first — Funnel exposes shells".
    On success show the same `https://<dnsName>` + a red "anyone with the URL can
    reach this — auth is your only gate" line.

Copy uses the existing sync `execCommand('copy')` fallback pattern (see the
terminal copy helper) — clipboard API alone is unreliable.

## D. Recipes (static, in the card, collapsed)

Two copy blocks with the daemon's real port interpolated (`config.port`):

- **Cloudflare Tunnel** (custom domain, public — needs CF Access):
  ```
  cloudflared tunnel --url http://localhost:<port>
  # or a named tunnel + Cloudflare Access policy (recommended — exposes shells)
  ```
- **Caddy reverse proxy** (own domain, public):
  ```
  coxpit.example.com {
    reverse_proxy 127.0.0.1:<port>
  }
  ```
Each with a one-line "public = shells exposed; keep coxpit auth on" caveat.

## Non-goals (restate in code comments)

- coxpit never runs a hosted relay or issues a coxpit-branded public URL.
- No bundling tailscale/cloudflared — detect and drive; absent → recipe.
- No persistence: serve/funnel truth is read from the CLI each `GET /api/remote`.

## e2e additions

Tailscale/Funnel need a real tailnet → cannot run in CI. Test what's deterministic:
1. `GET /api/remote` returns a well-formed `RemoteState` (in CI, `tailscale:"missing"`
   is the expected value — assert the shape and that it never 500s).
2. **Funnel auth guard (unit-ish)**: boot a daemon with auth on + empty pass is
   already the e2e's auth section — add: `POST /api/remote/funnel {on:true}` →
   `409` with `code:"NO_AUTH"`. (Serve is not gated.)
3. Board assets: `id="remoteOverlay"`, the recipe port interpolation
   (`reverse_proxy 127.0.0.1:` present in served HTML).
Live-only (owner, not CI): `serve --bg` → open `https://<dnsName>` from a phone.
