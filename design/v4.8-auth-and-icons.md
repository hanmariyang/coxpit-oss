# v4.8 — access-key auth & the icon system (detailed design)

Two product-polish changes:
1. **Auth UX** — replace the browser's native Basic-Auth popup (`admin` / password) with
   a **branded access-key unlock page** + a **first-run setup** ("this is your coxpit —
   set a key"). Self-hosted, single-owner, **no accounts, no sign-up**. Session cookie so
   you unlock once per device. Identity providers (CF Access / Tailscale) stay an **opt-in
   delegation** (`COXPIT_AUTH_DISABLED=1`) — the built-in key auth is the default because
   most self-hosters have no Cloudflare domain.
2. **Icon system** — replace system emoji / unicode glyphs with an inlined **Lucide** icon
   set (ISC license — MIT-safe), as a self-contained `<symbol>` sprite (no CDN; the board is
   one HTML string under a strict CSP). `currentColor` inheritance keeps status colors.

**Visual source of truth (approved):** `scratchpad/coxpit-auth-artifact.html` and
`scratchpad/coxpit-icons-artifact.html`. Match the board tokens.

Ships as **4.8.0**. Two phases (A auth, B icons) — both touch `board.ts`, so sequential.

## Part A — access-key auth (`src/auth.ts`, `src/server.ts`, `src/board.ts`, `src/config.ts`)

### A1. Key storage & precedence
- Persist the owner's key **hashed** in the data dir: `~/.coxpit/auth.json` =
  `{ algo:'scrypt', salt, hash, cookieSecret }` (32-byte random `cookieSecret` for signing).
  Use node's built-in `crypto.scryptSync` (N=16384) + `randomBytes` — **no new deps**.
- Precedence in `config`/gate:
  1. `COXPIT_AUTH_DISABLED=1` → no auth (delegated to a front gateway).
  2. Else if `COXPIT_AUTH_PASS` env is set → that is the key (back-compat; the resident's
     current AUTH.txt password keeps working — now entered on the branded page, no username).
  3. Else if `auth.json` exists → use the stored key.
  4. Else → **first-run setup mode** (no key configured yet).
- `COXPIT_AUTH_USER` is **dropped from the UX** (key-only). Basic-auth back-compat may still
  accept `anything:<key>` for automation, but the page never asks for a username.

### A2. First-run setup (security-critical — anti-claim)
When no key is configured, `GET /` serves a **setup page** ("Protect this coxpit — set an
access key"). Setting the key is allowed **only** when the request is provably the owner:
- **Primary path — setup token (Jupyter-style):** on boot with no key, print a one-time
  `COXPIT_SETUP_TOKEN` (random hex) to the daemon log (`~/Library/Logs/coxpit-oss/…`, i.e.
  stdout). `POST /api/auth/setup { key, token }` requires it. The owner has log access = owns
  the machine; this works through a tunnel/tailnet/localhost regardless of proxy topology.
- **Convenience path — genuinely-local:** also accept setup when the connection is loopback
  **and** carries no forwarding headers (`x-forwarded-for` / `cf-connecting-ip` absent) — a
  direct `http://127.0.0.1:8210` visit. A tunneled request (which arrives from 127.0.0.1 *with*
  CF headers) does NOT qualify — it must use the token.
- On success: hash+store the key, mint the session cookie, return ok. Setup is single-shot
  (once a key exists, `/api/auth/setup` 409s).

### A3. Unlock + session
- `POST /api/auth/unlock { key, remember }` → verify against the configured key (env or
  stored, constant-time compare of scrypt hashes) → on success set a **signed session
  cookie** `coxpit_sess` (httpOnly, SameSite=Lax, Secure when `x-forwarded-proto=https` /
  tunneled; `Max-Age` 30d if `remember` else session). Value = HMAC-SHA256 over an expiry
  stamp using `cookieSecret` (or a secret derived from the env key when env-mode). No server
  session store needed (stateless signed cookie).
- **Rate-limit:** per-client (keyed by `cf-connecting-ip` || `x-forwarded-for` || socket ip)
  in-memory attempt counter with backoff — after 5 fails, reject for a growing window (e.g.
  5s→30s→2m), surfaced as "try again in Ns (K attempts left)". Reset on success.
- `POST /api/auth/logout` → clear the cookie.

### A4. Gate rewrite (`authGate`)
Order: `COXPIT_AUTH_DISABLED` → pass; EXEMPT paths (unchanged: health, capture, bookmarklet,
agent subtasks, share/*) → pass; **valid `coxpit_sess` cookie** → pass; **valid Basic header
with the key** (automation back-compat) → pass; else:
- For an **HTML GET** (`accept: text/html`) → serve the **login page** (200 with the page, not
  a 401 popup) — setup page if no key configured, else unlock page.
- For **API / WS / non-HTML** → `401 {error:'unauthorized'}` (no `WWW-Authenticate` Basic
  header anymore, so browsers don't pop the native dialog on XHR).

### A5. Login / setup page (`src/board.ts` or a small separate template)
Match the approved auth mock: centered card, coxpit mark, **no username**, one access-key
field (+ confirm on setup), "Remember this device", rate-limit error line, a footer link
"Fronting with Cloudflare Access / Tailscale? →" (to README remote docs). It POSTs to the
A2/A3 endpoints via fetch, then reloads into the board on success. Keep it in the same
self-contained HTML style; it uses the Part-B icons (lock/unlock).

### A6. Key reset (documented)
`coxpit reset-key` CLI subcommand (or documented `rm ~/.coxpit/auth.json && restart`) →
clears the stored key → next boot is first-run setup again. Note in README + `bin/coxpit.js`.
Never log the key or the cookie secret.

## Part B — Lucide icon system (`src/board.ts`)

### B1. Sprite
Inline a `<svg style="position:absolute;width:0;height:0"><symbol id="i-…" viewBox="0 0 24 24">…</symbol>…</svg>`
at the very top of the board `<body>` (and the login page). Icons are **real Lucide SVG
paths** (ISC). The set (extend as needed): `lock, unlock, terminal, folder, git-branch,
git-merge, play, check, x, refresh-cw, file-text, code, image, message-square, chevron-right,
plus, pencil (steer), recycle (reclaim), settings, download, external-link, eye, alert-triangle
(missing-deliverable ⚠), circle (status dot fallback)`.

### B2. CSS + usage
`.ic{ width:1em; height:1em; stroke:currentColor; fill:none; stroke-width:2; stroke-linecap:round;
stroke-linejoin:round; vertical-align:-.125em; flex:none }`. Use `<svg class="ic"><use href="#i-x"/></svg>`.
Size via font-size / explicit width where needed; color via `currentColor` (so status classes
tint them automatically).

### B3. Replacement map (replace, don't leave both)
Swap the system emoji / ASCII-glyph icons across the board with `<use>`:
- terminal `>_` → `i-terminal`; Browse/repo folder → `i-folder`; base-branch `⎇` → `i-branch`;
  Merge → `i-merge`; Run/play → `i-play`; done `✓`/status → `i-check`; close `×` → `i-x`;
  refresh → `i-refresh-cw`; Reclaim `♻` → `i-recycle`; steer/수정 → `i-pencil`.
- Output cards: answer `◆` → `i-message-square`; doc `▤` → `i-file-text`; page `◱` → `i-image`
  or a browser glyph → keep `i-image` for image, use `i-file-text`/`i-code` appropriately;
  code `<>` → `i-code`; file → `i-image`/`i-file-text`.
- Missing-deliverable `!`/⚠ → `i-alert-triangle`; chevron `›`/`▸` → `i-chevron-right`; `＋` →
  `i-plus`; remote/link → `i-external-link`.
- **Leave** purely-textual arrows in prose (→) and the `⌒`/`⌁` goal-band glyph if it reads as
  a mark (or map to a small icon — designer's call, keep consistent). Status **dots** can stay
  CSS circles (they're not emoji).
Do NOT introduce a second rendering of the same thing; each swap removes the old glyph.

### B4. Attribution (license hygiene)
Lucide is ISC — its license requires the copyright notice be retained. Add a `NOTICE` (or a
`licenses/lucide.txt`) with the Lucide ISC copyright, and a one-line credit in README
(“Icons: Lucide (ISC)”). Audit stays clean (no runtime dep added — paths are inlined).

## Phasing (each an e2e-green commit; orchestrator verifies + commits per phase)

- **Phase A — auth**: A1–A6. e2e: fresh daemon (no key, `COXPIT_AGENT` etc.) → `GET /` html
  returns the **setup** page; `/api/auth/setup` without token/local → 403, with token → sets
  key + cookie; after setup `GET /` returns board (cookie) / unlock page (no cookie); wrong
  key rate-limited; API without auth → 401 **without** `WWW-Authenticate`; `COXPIT_AUTH_PASS`
  env mode → unlock with that key works; EXEMPT + share still open. Live: setup→unlock→board
  round-trip; cookie persists.
- **Phase B — icons**: B1–B4. e2e (UI contract): board serves the `#i-terminal`/`#i-lock`
  sprite symbols + `.ic` usage; no leftover of the replaced emoji in served HTML (spot-check a
  couple). Live: render board + login page, confirm icons draw (no missing-glyph), no pageerror.

Each: `npm run typecheck` clean + `bash test/e2e.sh` green (bash-3.2 rules) + board JS parses.
No version bump by the implementer. After B: orchestrator cuts 4.8.0 (standard train).

## Guardrails
- **Setup anti-claim is security-critical**: a publicly-exposed fresh daemon must NOT let a
  stranger set the key — enforce the token / genuinely-local rule; a tunneled request needs the
  log token. Constant-time key compare; scrypt; never log key/secret/cookie.
- No `WWW-Authenticate: Basic` anymore → no native popup; the page is the UX.
- `board.ts` template-literal rules (`\n`, escaped backticks, esc()/escA()); the sprite and
  login page are large additions — keep them valid.
- No new deps (crypto is built-in; icons inlined). No GPL/AGPL; Lucide ISC noticed.
- Resident back-compat: env `COXPIT_AUTH_PASS` (current AUTH.txt) keeps working → after
  upgrade the resident shows the branded unlock page asking for that same key (no username),
  no re-setup needed. Document this.

## Definition of done
Branded unlock + first-run setup (anti-claim) + session cookie replace the Basic popup;
username gone; Lucide icons replace system emoji across board + login. e2e green; live-verified.
Then 4.8.0 via the standard train (bump both package.json + desktop, locks, tag, hardened CI,
owner npm publish, resident upgrade — the resident's existing key still unlocks via the page).
