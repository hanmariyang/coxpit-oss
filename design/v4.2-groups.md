# v4.2 — the board knows its groups (detailed design)

One theme: five runs born from one goal must not look like five strangers.
Two origins of "related work" exist today and neither is visible:
- plan fan-out siblings — **no record at all** that they share a goal
- agent-spawned subtasks — recorded (`tasks.parentRunId`) but only shown as a meta chip

---

## A. Group model

**Schema**:

```sql
CREATE TABLE IF NOT EXISTS task_groups (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  kind TEXT NOT NULL DEFAULT 'goal',   -- 'goal' | 'swarm'
  title TEXT NOT NULL,
  created_at INTEGER DEFAULT (unixepoch())
);
-- tasks: ALTER TABLE tasks ADD COLUMN group_id INTEGER   (idempotent try/catch)
```

**Stamping rules** (`src/orchestrator.ts`):
1. `planFanout`: before creating tasks, insert one `task_groups` row
   `{kind:'goal', title: goal.slice(0,140)}`; every created task gets its `groupId`.
   Applies to dry (rehearsal) plans too — the pipeline must match real.
2. `spawnSubtasks`: resolve the parent run → parent task.
   - If parent task has `groupId` → child task joins it.
   - Else → create `{kind:'swarm', title: parentTask.title}` group, then **backfill
     the parent task's `groupId`** with it (so parent and children band together),
     and stamp the child.
3. Manual tasks and workbenches: `groupId` stays NULL — they render exactly as today.

**API**: `/api/fleet` response adds `groups: task_groups[]` (all rows; they're tiny).

## B. Group bands on the board

**Rendering model** — the grid stays a grid of first-class run cards; grouped cards
are simply *clustered inside a band container*, ungrouped cards flow after.

Ordering inside `render()`:
1. Partition runs by `tasks.get(taskId).groupId`.
2. Bands sorted by group id desc (newest goal first), then ungrouped runs in the
   current order.
3. Inside a band: runs sorted by run id asc.

**Markup** per band:

```html
<div class="gband" data-g="7">
  <div class="gband-h">
    <span class="gband-glyph">⌁</span>
    <span class="gband-t">improve the docs</span>
    <span class="gband-n">5 tasks · 3 settled</span>
    <span class="gband-sp"></span>
    <button class="btn-ghost sm" data-gsel="7">Select runs</button>
    <button class="btn-ghost sm" data-gclose="7">Close group</button>
    <button class="gband-fold" data-gfold="7">▾</button>
  </div>
  <div class="gband-grid"><!-- run cards, unchanged markup --></div>
</div>
```

**CSS** (respecting the house rule: no left accent bars, no color fills as decoration):

```css
.gband{border:1px dashed var(--line-hi);border-radius:14px;padding:12px;margin-bottom:14px}
.gband-h{display:flex;align-items:center;gap:10px;margin-bottom:10px;font-family:var(--mono)}
.gband-glyph{color:var(--brand);font-size:13px}
.gband-t{color:var(--ink);font-size:12.5px;font-weight:600;overflow:hidden;white-space:nowrap;text-overflow:ellipsis}
.gband-n{color:var(--faint);font-size:11px}
.gband-sp{flex:1}
.gband-fold{background:none;border:none;color:var(--muted);cursor:pointer;font-size:12px}
.gband.folded .gband-grid{display:none}
.gband-grid{display:grid;grid-template-columns:repeat(auto-fill,minmax(360px,1fr));gap:14px}
@media (max-width:860px){.gband-grid{grid-template-columns:1fr}}
```

"settled" in the counter = every run of the task is in
{done, failed, stopped, merged} (a task counts settled when all its runs settled).

**Fold state**: localStorage `coxpit.gfold` = array of folded group ids. WS `render()`
re-applies it (bands re-render every update — fold must survive).

**Swarm bands**: `kind:'swarm'` uses glyph `↳` and title `swarm of: {parent title}`.
Subtask cards keep their existing `↳ by rN` meta chip (band + chip are complementary).

## C. Attempt counters

For any task with more than one run, every card's meta row gains
`<span class="attempt">run {i}/{n}</span>` — `i` = 1-based index of the run within
its task (ordered by run id), `n` = total runs of the task. Applies to grouped AND
ungrouped tasks (a plain ×3 fleet gets counters too — this is the fix for
"same title, three cards, which is which").

CSS: `.attempt{color:var(--brand);opacity:.8}` (mono inherited from `.meta`).

---

## D. Group actions

**Select runs** (band header): enters the existing select mode and pre-selects all
*selectable* runs of the band (same eligibility as manual selection today —
settled with changes). Implementation: reuse `selToggle` machinery; do not fork
the selbar. The user then presses Integrate on the existing floating bar —
group → Integrate is thereby two clicks, no new merge path to test.

**Close group**: iterate the band's tasks through the SAME close endpoint,
sequentially, honoring the v4.1 close guard: call without force; collect every
409 `atRisk` across tasks into ONE `confirmUI` (danger) listing all at-risk runs;
on OK, re-close all with `force:true`. Toast the aggregate ("closed 5 tasks").

**No group review** in this milestone — review stays per-task in Compare
(a cross-task judge is a different, larger feature; not in scope).

## e2e additions

1. `POST /api/plan` (dry) → both created tasks share one non-null `groupId`; fleet
   `groups` contains one row with `kind:"goal"`.
2. Board HTML contains `gband-h` and `class="attempt"` (asset presence).
3. Subtask flow (needs a real-run token — skip in CI): instead unit-test stamping:
   dry plan → spawnSubtasks not needed; assert via API that a manually created task
   has `groupId: null` (control).
4. Close-group has no dedicated endpoint (client loop) → covered by 4.1's close
   guard checks.
